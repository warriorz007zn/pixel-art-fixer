# Fork 维护与上游同步规范

状态：已采纳。日期：2026-09-21。

适用于 [warriorz007zn/pixel-art-fixer](https://github.com/warriorz007zn/pixel-art-fixer)。目标是在保留本仓库定制功能的同时，有选择、有验证地吸收上游改进。

## 1. 仓库边界与决策

- `origin`：`https://github.com/warriorz007zn/pixel-art-fixer.git`，我们维护的公开 fork。
- `upstream`：`https://github.com/Retro-Diffusion/pixel-art-fixer.git`，原作者仓库。
- `pixel-inspector` 是另一个独立仓库。本规范不合并两者的源码、提交历史或发布流程。
- 上游更新不会自动改变我们的分支。默认不配置自动合并或强制同步；主动获取、审查、验证后再合入。
- 我们的 `main` 保存经过验证、实际使用的版本，不要求始终与上游 `main` 完全一致。

采用这套方式，是因为 Git 可以处理代码文本合并，但不能判断算法效果、接口兼容性和功能回退。没有合并冲突，不代表更新后行为正确。

## 2. 分支与提交

| 分支 | 用途 |
| --- | --- |
| `main` | 我们的稳定版本，包含已验证的定制功能与上游更新 |
| `fix/<问题>`、`feat/<功能>`、`docs/<主题>` | 短期改动分支，验证后通过 PR 合入自己的 `main` |
| `sync/upstream-<日期或版本>` | 从自己的 `main` 创建，用于引入上游更新、解决冲突、验证 |

每个提交只解决一个明确问题，避免把大规模格式调整、重构和行为变化混在一起。能用独立模块、参数或外层调用实现的功能，尽量不大范围改写上游核心。定制功能应有对应测试和简短说明，便于以后迁移或移除重复实现。

同步上游的 PR 使用 **merge commit** 合并，保留上游提交的祖先关系；不要把整批上游同步 squash 成一个补丁或用 rebase 重写已共享的 `main`。普通功能或文档 PR 可按其规模选择常规合并或 squash。

本规范是维护约定，不表示仓库已经配置了分支保护、必需检查或自动化。若要增加这些平台设置，应单独实施并验证。

## 3. 每次同步流程

### A. 获取信息，不直接改动稳定版本

1. 确认当前工作目录属于本仓库，检查 `git remote -v`，防止操作到 `pixel-inspector` 或向上游误推送。
2. 确保工作区干净。未完成改动应先妥善提交或保存，不带着未提交修改执行同步，也不丢弃未知改动。
3. 获取 `origin` 和 `upstream`，记录自己的基线 SHA、上游目标 SHA。
4. 阅读上游新提交及版本说明，标出接口、算法、依赖、许可证和输入输出行为变化。

以下命令在本仓库根目录执行；示例分支名中的日期应替换为本次日期，分支应为新名字：

```sh
git status --short
git remote -v
git fetch origin
git fetch upstream
git switch main
git merge --ff-only origin/main
git rev-parse HEAD upstream/main
git log --oneline HEAD..upstream/main
git diff --stat HEAD...upstream/main
```

`fetch` 更新远端跟踪引用，不修改当前工作文件。若 `--ff-only` 失败，说明本地与远端已分叉，应先检查原因；不能接着强制覆盖。

### B. 在同步分支合并

```sh
git switch -c sync/upstream-20260921
git merge --no-ff --no-commit upstream/main
```

- `--no-commit` 便于检查合并结果，不是测试的替代品。
- 有冲突时逐项解决，检查冲突标记和最终差异，暂存明确处理过的文件。
- 无冲突也要检查自动合并的结果，尤其是接口契约和默认参数。
- 如需放弃尚未提交的合并，在本次合并前工作区干净的前提下，可用 `git merge --abort`。若 Git 提示已经是最新状态，则没有待中止的合并。

### C. 验证后提交与审查

1. 执行第 5 节的验证，记录实际命令、环境与结果；无法执行的检查注明原因，不写成“通过”。
2. 完成合并提交，将同步分支推到 `origin`，创建以 **本 fork 的 `main`** 为目标的 PR。
3. PR 中填写第 7 节记录，复核保留、替换和暂缓的内容。
4. 满足验收要求后合并；若还有未解决的回退，继续修复或暂缓升级，保持 `main` 不变。

暂存和提交前可检查：

```sh
git status --short
git diff --check
git diff --cached --check
git diff --cached
```

上述命令不是测试套件。应根据实际改动运行项目对应的功能测试、构建和图片对比。合并完成后，本地 `main` 再从 `origin/main` 快进更新。

## 4. 冲突与取舍原则

| 情况 | 处理方式 |
| --- | --- |
| 修改位置互不重叠 | 接受自动合并作为候选，仍需验证组合后的行为 |
| 双方修复同一个问题 | 比较完整性和兼容性，保留更合适的实现，删除已被取代的重复补丁 |
| 上游改进算法，我们增加手动参数或批处理能力 | 尽量保留双方能力，让定制功能适配新接口 |
| 上游总体改善，但目标场景明显退步 | 定位原因；修复、提供有测试的显式模式，或暂缓升级 |
| 上游大规模重构 | 把我们的功能迁移到新结构，避免机械保留旧代码形成两套重复内核 |
| 只急需一个独立修复 | 可例外使用 `cherry-pick`，先检查依赖，并记录原提交 SHA、选择原因及后续整合计划 |

不能仅凭代码新旧决定取舍，也不能整批选择“全部用我的 / 全部用上游的”来消除冲突。判断对象是双方改动要保留的行为，而不只是同一行文字。

正常上游跟进以完整 merge 为主。长期零散 cherry-pick 会增加依赖和重复补丁的维护成本；未来整批合并时需核对已引入的补丁。

禁止为“追平上游”对我们的 `main` 执行强制推送、丢弃本地提交的 reset，或选择会丢弃定制提交的强制同步选项。

## 5. 验证标准

验证至少回答两个问题：上游的改进是否有效？我们依赖的行为是否保留？

### 功能与兼容性

- 根据改动覆盖 Python API、CLI、输入限制、输出尺寸、透明度、默认参数与手动参数。
- 改动涉及 Rust 时执行相应构建与测试；若涉及两种实现共享行为，比较 Python 与 Rust 的结果，差异需解释。
- 新增功能和修复补回归测试，不通过跳过测试、降低已有阈值或删除断言来获得通过状态。
- 对同步前已存在的问题建立基线，区分旧缺陷与本次新增回退；不把旧缺陷掩盖成正常行为。
- 纯文档改动只需检查事实、链接、命令语义和差异，不要求为其运行图像算法测试。

### 图像效果

在相同输入、参数和可比环境下，比较 **我们当前版本、上游目标版本、合并候选版本**。优先固定随机种子和依赖版本；若存在非确定性，应注明并验证结果是否稳定。

关注：输出尺寸、网格判断、角色轮廓和关键细节、透明边缘、颜色变化，以及相关性能和内存变化。检测器报告的 confidence 不能单独作为质量证据，漂亮的预览也不能证明恢复了原生分辨率。

初始回归场景应包含：

- 干净的整数倍最近邻放大图，具有已知原生尺寸。
- 非整数缩放、模糊、透明边缘与多帧排布等代表性输入。
- 已知困难场景：早期测试中，一张 1536×1024 的六帧角色图在自动 full 模式下被缩到 26×23。这个案例用于提醒我们检测灾难性细节丢失，不把人工选择的某个尺寸当作未经证明的真值。

公开测试只提交有明确使用与再分发权利的素材。私人或授权不明确的图片留在本地；可用自制的合成素材建立公开测试。不要把工作目录中的参考图顺手提交到这个公开 fork。

### 验收结论

- 接受：相关检查通过，定制能力保留，已知差异有解释。
- 有条件接受：明确的行为变化经维护者接受，文档及测试随之更新。
- 暂缓：存在未解决的功能或效果回退，或缺少足以判断的验证证据。

## 6. 回退与减少长期维护成本

- 同步前记录稳定基线 SHA；正式发布可另打版本标签。
- 尚未合入 `main` 的失败尝试留在同步分支处理，不影响稳定版本。
- 已共享版本需要回退时，使用新的 revert 提交保留历史，不强制重写 `main`。
- 回退 merge commit 前确认父提交和受影响内容；例如 `git revert -m 1 <合并提交>` 只有在第一个父提交确为要保留的稳定基线时才适用。
- 回退合并后，Git 仍记得这些上游提交已合入过；后续重新引入需规划修复提交或撤销该 revert，不能以为再次 merge 同一版本就能恢复全部变化。
- 适合上游的通用修复优先整理成小 PR；对外提交 PR 需在该次工作中获得授权。上游接受后，可减少我们独立维护的差异。
- 保留原 [MIT 许可证](../LICENSE) 与版权声明；引入新依赖、素材或分发方式时核对对应许可。

## 8. 后续修改本规范

这份文档记录已经接受的维护方式。若将来需要自动同步、变更分支策略或改变发布方式，先明确新的目标和风险，再在文档及相应 PR 中记录修改理由。不能为了省略一次验证而临时降低标准。
